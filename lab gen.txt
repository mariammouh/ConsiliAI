The starting materials
 
Before the Lab Generator even runs, it needs three things handed to it:
 
A lesson — one lesson from Course Generator, which already has a title, a summary, and a breakdown into topics (called sections) — e.g. "Definition of fake news," "Encoder-decoder structure," etc. Each topic already has its own explanation and supporting evidence pulled from the paper.
The module it belongs to, and the analyzed papers it's grounded in.
A list of similar real repos, scored by how relevant they are to the idea (reused from your Similar-Project Agent).
Stage 1 — Gathering grounding material
 
The system pulls the actual text of the relevant paper sections (via _get_paper_analysis_by_title) and, if a real GitHub/GitLab repo scored above the 0.35 similarity threshold, grabs its description and README excerpt too. If nothing cleared the threshold, it just says "no similar project found" rather than inventing one. This raw material — paper text + repo text — gets reused in every prompt from here on, so every step has the same source of truth.
 
Stage 2 — The scaffold (Groq writes the "spec sheet")
 
One call to Groq produces a JSON object — think of it as the exercise's blueprint, not any code yet:
 
exercise_title, learning_objective, instructions (what the student sees), difficulty, hints
format: is this a real coding exercise (notebook/fill_in_blank) or purely conceptual (no code needed)? If the topic genuinely has nothing to implement, Groq is instructed to say so honestly rather than force code where there isn't any.
code_plan — this is the important one. It's a numbered list, one entry per topic, and for each topic Groq writes: what this step should accomplish (goal), the exact names it must create — function names, class names (produces), and which earlier step's names this step depends on (uses). Think of it as a flowchart written as JSON. This plan is the thing every later check compares the actual code against.
 
If format comes back conceptual, the pipeline stops here — no code gets written, because none is needed.
 
Stage 3 — Writing the code, one topic at a time
 
This is the "decomposition" part. Instead of asking a model to write the entire exercise's code in one giant response (which is where cross-referencing bugs like "uses a variable that was never created" tend to happen), the system loops through the topics one at a time, in order.
 
For topic 1: the coder model (Qwen locally, or Groq/Gemini if you route there) gets the topic's own explanation, the matching code_plan step's produces/uses contract, and told "this is the first step, include whatever setup you need." It writes back two code blocks: a STARTER version (with the core logic replaced by # TODO comments) and a SOLUTION version (the real implementation).
 
For topic 2 onward: the model additionally gets everything written in previous steps, with an explicit instruction: "this already ran successfully, don't repeat it, only add what THIS step needs." That's the mechanism that's supposed to stop reimplementation — each step is told what already exists so it can build on it instead of rewriting it.
 
Each step's code gets glued onto a running total (accumulated_starter, accumulated_solution), with a small comment marker between sections.
 
Optional: multiple candidates per step. If you ask for num_candidates > 1, the system generates several independent attempts for that one topic, silently scores each one with the same static checks used later (no extra LLM calls — just fast local analysis), and keeps only the best-scoring version before moving to the next topic. This is free for local models, costly for cloud ones.
 
Stage 4 — Validation (reading the code without running it)
 
Once the full accumulated code is assembled, _validate_python_code checks it, purely by parsing it as a syntax tree — nothing is ever executed. Four separate checks happen here:
 
Does it even parse? — a straightforward syntax check.
Undefined names — is any name used anywhere in the file that was never defined anywhere (not imported, not assigned, not a builtin)?
Used-before-defined — a stricter, order-aware check: is a name used at the top level of the file before the line that actually creates it (like train_df referenced before the train_test_split that builds it)? This one deliberately skips code inside functions, since Python resolves those names when the function is called, not when it's defined — so a function referencing something defined later in the file is completely normal and shouldn't be flagged. It also correctly walks into if/for/while/try blocks step-by-step (since those run immediately too), and correctly ignores names bound by list comprehensions (since those are self-contained and don't leak into the surrounding order).
Duplicate definitions — is the same class/function name defined more than once at the top level, with a nearly identical body the second time? That's a fingerprint of a model re-emitting old work instead of extending it, rather than a legitimate "replace a stub with the real thing" pattern (which looks very different the second time, so it isn't flagged).
 
Any failure here sets the whole thing invalid.
 
Stage 5 — Repair (giving the model a second chance, with the exact error)
 
If validation failed, the system doesn't just discard the code. _repair_code sends the broken code back to the coder model along with a plain-English description of exactly what's wrong (built by _build_repair_prompt) — e.g. "these names are used before the line that creates them: X, Y — reorder the code." It tries up to 2 times, re-validating after each attempt, and stops as soon as it's clean. If two attempts still leave it broken, one last resort (_rewrite_code) asks for a full rewrite of the whole block rather than a surgical patch.
 
Stage 6 — Plan compliance (does the code match what it promised?)
 
This is separate from Stage 4 — it doesn't ask "is this valid Python," it asks "does this code actually do what the plan from Stage 2 said it would." Three checks, purely by comparing names, not meaning:
 
missing_produces — a name the plan said a step would create, that never actually got defined anywhere. This blocks the lab — it means a whole planned piece was silently skipped.
unplanned_definitions — a name that exists in the code but was never in the plan. This is recorded but does not block, because testing showed it constantly flagged completely normal helper functions (e.g., a preprocessing function feeding into a planned training function) — punishing that would reject good code for no reason.
unused_dependencies — a step's plan says it depends on an earlier step's output, but that name is never referenced anywhere in the whole file. This is the check built specifically to catch the HetTransformer bug — a class claiming to build on TransformerModel but silently reimplementing the same logic from scratch instead. This one blocks, since there's no legitimate reason to declare a dependency you never use.
 
If this check fails, it gets one dedicated repair attempt with the specific mismatch explained.
 
Stage 7 — Quality check (is the "solution" actually complete?)
 
One more pass, only on the solution code, never the starter (since starter is supposed to have blanks). It looks for leftover TODO comments, NotImplementedError, or functions whose entire body is just pass or a lone docstring — things that shouldn't exist in something claiming to be a finished answer key. One more dedicated repair attempt if this fails.
 
Stage 8 — The honest fallback: debug mode
 
If, after all of that, the solution still fails — but only for reasons the validator genuinely understands (a real syntax error, an undefined name, a real plan mismatch) — the system doesn't throw the lab away. It relabels the exercise as an intentional debugging challenge: the student sees the broken code plus a hint calibrated to difficulty (more specific for beginners, vaguer for advanced), and the teacher's version shows the actual validator findings instead of pretending there's a verified correct answer. This conversion is deliberately never applied to bugs the system can't see (a wrong library call, hallucinated content) — because it would be dishonest to imply "there's a findable bug here" when the system has no idea whether there is one.
 
Stage 9 — Turning it into a real notebook
 
Finally, export_lab_to_notebook builds two actual .ipynb files, no LLM involved — pure formatting. If nothing needed repair, it renders one markdown header + one code cell per topic, matching the lesson's own structure — nicer for a student to follow than one giant blob. If repair did rewrite the flat code, the per-topic breakdown is dropped in favor of one combined cell, since the original topic-by-topic pieces would no longer reliably match the patched version. Debug-mode labs get their own special layout: a warning banner, the buggy code, and (in the teacher's copy) the raw validator report instead of an answer key.

The validator is in `tools.py:2679-3030`. It uses Python’s `ast` module to inspect code structurally without executing it.

## 1. Parse source into an AST

```python
tree = ast.parse(code)
```

Python converts source text into a tree of nodes:

```python
x = model.predict(data)
```

roughly becomes:

```text
Assign
├── Name("x", Store)
└── Call
    ├── Attribute
    │   └── Name("model", Load)
    └── Name("data", Load)
```

`Store` means “this statement creates or assigns this name.”  
`Load` means “this statement reads this name.”

If parsing fails, validation stops immediately:

```python
{
    "syntax_ok": False,
    "syntax_error": "...",
    "valid": False
}
```

This catches malformed Python, but does not run imports, functions, or APIs.

## 2. First pass: collect all names

`NameAnalyzer`, a subclass of `ast.NodeVisitor`, walks the entire tree:

```python
NameAnalyzer().visit(tree)
```

It collects three sets:

```python
assigned_names
imported_names
used_names
```

### Assigned names

These count as definitions:

```python
model = ...
```

The `Name("model", Store)` node adds `model`.

```python
def train(data):
    ...
```

The `FunctionDef` node adds `train`.

Function arguments are also added:

```python
def train(data, epochs):
    ...
```

adds `train`, `data`, and `epochs`.

Classes, loop variables, exception variables, and ordinary assignments are handled similarly.

### Imported names

```python
import pandas as pd
from sklearn.model_selection import train_test_split
```

adds:

```python
pd
train_test_split
```

### Used names

Any `Name` node with `Load` context is recorded:

```python
result = model.predict(data)
```

records:

```python
result   # Store
model    # Load
data     # Load
```

The validator then reports a name as globally undefined if it is:

- used
- not assigned anywhere
- not imported
- not a Python builtin
- not in the explicit whitelist

Example:

```python
result = model.predict(data)
```

would report:

```python
undefined_names = ["data", "model"]
```

This is a whole-file existence check, not a full Python scope analyzer.

## 3. Builtin and whitelist filtering

The validator allows Python builtins such as `len`, `list`, `print`, and `range`.

It also explicitly permits names such as:

```python
__name__
__file__
self
cls
```

This prevents normal Python names from being incorrectly reported as undefined.

## 4. Second pass: check use-before-definition

The first pass only asks:

> Does this name exist somewhere in the file?

The second pass asks:

> At the point where this name is used, has it already been defined?

For this, `_own_uses_and_defs(stmt)` examines one statement and returns:

```python
uses, defs
```

Example:

```python
predictions = model.predict(data)
model = create_model()
```

The first statement has:

```python
uses = {"model", "data"}
defs = {"predictions"}
```

The second has:

```python
uses = {"create_model"}
defs = {"model"}
```

Since `model` is eventually defined, it is classified as `used_before_defined`.

The validator first flattens immediate-execution code with `_flatten_immediate()`:

```python
if condition:
    x = 1
```

becomes an ordered sequence containing:

```text
if condition
x = 1
```

It descends into:

- `if`
- `for`
- `while`
- `with`
- `try`
- exception handlers

But it deliberately does not descend into function, class, or lambda bodies. Those bodies execute later, when called.

Then it tracks:

```python
defined_so_far
```

For each statement:

1. Find names used by this statement.
2. Report names not yet in `defined_so_far`.
3. Add this statement’s definitions to `defined_so_far`.

Example:

```python
data = load_data()
model = train(data)
```

is valid because `data` is defined before it is used by `train(data)`.

## 5. Why function bodies are skipped for ordering

This is considered valid by the validator:

```python
def predict():
    return model.predict(data)

model = create_model()
data = load_data()

predict()
```

The function is defined before `model` and `data`, but its body does not execute at definition time. By the time `predict()` is called, both names exist.

The validator therefore checks the function’s existence but does not treat its internal references as module-level ordering errors.

## 6. Compound statement handling

For this code:

```python
for row in rows:
    value = transform(row)
```

the validator checks:

- `rows` in the loop header
- `row` as a definition
- `value` as a definition
- `transform` as a used name inside the loop body

This is why `_flatten_immediate()` recursively walks loop and conditional bodies: those bodies can execute immediately.

## 7. Module-level undefined names

After the ordering pass, it separately checks names used at immediate/module level that are never defined there.

This catches cases like:

```python
def create_data():
    train_df = ...

print(train_df)
```

`train_df` exists inside `create_data`, but that function is never called and does not create a module-level variable. The validator reports it in:

```python
module_level_undefined
```

This is stricter than ordinary global undefined-name detection because a name may exist somewhere in the file but not in the scope where it is actually used.

## 8. Comprehensions

The code intends to treat comprehension variables as local:

```python
values = [row["score"] for row in rows]
```

Here, `row` should not be reported as undefined or used-before-defined. `row` is created by the comprehension’s `for row in rows`.



## 9. Duplicate definitions

At the end, `_find_duplicate_definitions()` checks repeated top-level functions/classes.

Example:

```python
def train():
    pass

def train():
    pass
```

It compares the source text of both definitions with `difflib.SequenceMatcher`.

If similarity is at least `0.85`, it marks the repetition as:

```python
likely_wasteful_repeat = True
```

That makes validation fail. Different implementations with the same name are recorded but are less likely to be rejected.

## 10. What the AST validator cannot detect

It does not execute code, so it cannot reliably detect:

```python
model.nonexistent_method(data)
```

It sees that `model` and `data` exist, but cannot know whether `nonexistent_method` is a real API.

It also cannot verify:

- tensor shapes
- dataset contents
- model accuracy
- runtime exceptions
- incorrect algorithm logic
- unavailable packages
- incorrect library method names

So the validator is mainly a structural safety net:

```text
parseable Python
+ names exist
+ module-level order is plausible
+ planned names are present
+ solution is not still a placeholder
```
